# ADR 001: Implement Task Status Filtering

**Status**: Accepted
**Date**: 2026-07-09

## Context
Users have too many tasks in the system, making it difficult to find relevant work. Currently, all tasks are returned in a single list, which is not scalable.

## Decision
We will add an optional `status` query parameter to the `GET /api/tasks/` endpoint. This allows the client or test suite to filter tasks by their system-defined states (`ToDo`, `InProgress`, `Done`).

## Alternatives Considered
* **Client-side filtering only**: Fetching all tasks and filtering in the UI. Rejected because it does not scale well as the database grows.
* **No action**: Leaving the current implementation as-is, leading to poor performance and user experience over time.

## Consequences
* **Positive**: Reduced payload size over the network and faster UI rendering cycles for active work items.
* **Negative**: The backend handler for `GET /api/tasks/` must be extended to accept an optional query parameter and filter the results accordingly.
